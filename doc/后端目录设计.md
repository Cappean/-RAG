# 医疗智能问诊后端目录设计

更新时间：2026-10-19。

## 1. 设计范围

采用按业务模块组织、模块内部再分层的模块化单体，使用 Python 3.13、uv、FastAPI、Pydantic 和 PyMongo Async。

当前先搭建框架，再逐步开发患者、问诊、知识库和 RAG。后台任务采用 `asyncio.Queue` 和内存状态字典，在 FastAPI 进程内运行协程 Worker，暂不引入 Redis、Celery 或其他消息中间件。

本文描述目标目录和代码职责，不表示下列文件已经实现。现有源码已删除，旧测试、打包配置和 CLI 入口仍需在框架开发时核对、调整；当前不能据此认定服务能够启动。

目录和内存任务方案以本文为准；数据字段以 [数据存储设计.md](数据存储设计.md) 为准。旧《后端项目框架设计》中的 `src/medical_consultation_backend`、MongoDB `jobs`、租约及独立 Worker 方案不再作为本次实现依据。

## 3. 业务模块内部结构

以患者模块为例：

```text
patient/
├── __init__.py
├── router.py        HTTP 路径、参数接收、响应和状态码
├── schema.py        Pydantic 请求与响应模型
├── model.py         持久化数据模型及字段转换
├── service.py       业务校验、流程组织
└── repository.py    MongoDB 查询、更新与数据映射
```

| 模块 | 负责内容 |
|---|---|
| `patient` | 患者基本信息、过敏史、既往史、用药信息 |
| `consultation` | 会话和消息持久化、生成状态、引用快照、SSE 输出 |
| `knowledge` | 文件去重、文档与切片元数据、MinerU 解析协调、切分和入库 |
| `rag` | 检索查询构造、稠密与稀疏召回、融合、重排、证据与回答校验、问诊编排 |

这四项是当前业务模块。`worker` 位于 `src/app/worker/`，提供内存任务执行和状态查询；存活检查位于 `modules/health.py`，两者属于公共能力。真实问诊通过 `consultation` 调用 `rag` Service，不要求 `rag` 单独暴露 HTTP 接口，也不以是否开发顶部搜索为前提。

附件、独立搜索、用户通知、动态组件状态和语音属于后续功能，不能仅根据页面入口或 URL 名称推定需要新增同名模块；代码归属在相应功能进入开发后确定。

`knowledge` 可按需要增加 `parser.py`、`splitter.py`、`ingestion.py`；`rag` 可增加检索、提示词和 LangGraph 节点文件。业务代码增长后再拆子包，不提前堆叠抽象。

`schema.py` 负责对外协议，`model.py` 负责存储结构；MongoDB ObjectId、UTC 日期等在边界转换。具体字段遵循数据存储设计，不能直接把内部数据库记录当响应返回。

## 4. 分层与依赖规则

普通请求的调用方向：

```text
Router → Service → Repository / 外部设施适配器
```

Router 负责 HTTP 协议，不直接查 MongoDB、调用模型或解析文件。Service 不依赖 FastAPI Request、Response、HTTPException，业务错误通过统一异常交给 HTTP 层转换。Repository 负责具体集合的数据操作，不生成医学回答、不组织入库流程。

`infrastructure` 封装外部 SDK、连接、超时和底层调用；文档是否可检索、是否重复上传等业务规则留在 Service。`core` 和 `common` 不反向导入业务模块，公共目录只收纳真正跨模块复用的能力。

跨模块通过明确的 Service 方法或数据结构协作，避免一个模块直接修改另一个模块的集合。只有确有多种实现或测试替换需要时才提取 Protocol，不统一创建 BaseService、BaseRepository 或 ServiceImpl。

`main.py` 负责应用组装：配置、异常处理、请求 ID、路由注册以及资源生命周期。共享客户端和任务队列通过应用生命周期创建、依赖注入使用、关闭时释放，避免在模块导入时启动连接和后台任务。

## 5. 内存后台任务

Demo 的执行路径：

```text
提交接口 → 内存队列 → 协程 Worker → 处理器 → 业务 Service
查询接口 → 内存任务状态字典
```

`queue.py` 封装提交与查询，调用方不直接操作队列或状态字典。`runner.py` 负责领取任务、更新执行状态和隔离单个任务异常；`handlers.py` 将任务类型映射到处理函数。后续文档处理器调用知识库 Service，不在消费循环里混写解析和向量化逻辑。

应用启动时创建队列和 Worker，关闭时停止接收任务并限时清理后台协程。任务参数传资源 ID 等必要信息；队列设置容量上限，已完成任务记录设置保留上限。队列满时明确拒绝提交，不报告任务已接收。

首次只实现模拟耗时任务，状态采用 `queued`、`running`、`succeeded`、`failed`，通过 UUID `taskId` 查询。任务执行失败记录适合对外展示的错误，避免泄露连接串、密钥和病历全文。任务 ID 在重启后失效，查询返回任务不存在。

API 必须单进程启动；多个进程的队列和字典不共享，开发热重载也会丢失任务。不提供持久化、租约、自动重试、独立 Worker 命令或重启恢复。同步解析与模型推理不能直接阻塞事件循环，后续根据库特性选择线程、进程或独立服务。

MongoDB 不建立 `jobs` 集合，文档状态仍写入 `documents.status`。接入真实文档入库时需处理重启后遗留的 `processing` 记录，具体约定见数据存储设计。

## 6. 公共工程约定

| 方面 | 约定 |
|---|---|
| 配置 | 使用 Pydantic Settings，配置集中管理，密钥不写入代码与前端 |
| HTTP | 接口统一使用 `/api` 前缀，错误包含 `code/message/details/requestId` |
| 响应 | 所有查询不分页，列表一次返回符合筛选条件的全部结果，不设计分页参数、游标或隐含条数截断；SSE 保持流事件协议，不强行包装为普通 JSON |
| 时间与 ID | 业务时间为 UTC，对外使用 ISO 8601；业务 ObjectId 对外转字符串 |
| 日志 | 请求 ID、耗时、异常摘要；医疗内容与密钥脱敏，开发日志继续放在 doc |
| 健康检查 | 存活检查只确认 API 进程，不把它描述为数据库或模型就绪 |
| 外部设施 | 按功能启用，框架启动不自动加载模型、解析文件或写入外部设施 |

鉴权和前端联调暂不实现，`ownerId` 预留规则遵循数据存储设计。`deploy` 本轮只预留目录，不要求安装 Docker 或启动消息中间件。

## 7. 测试与实施顺序

先核对现有测试，保留仍然适用的行为验证；旧租约和 MongoDB 任务仓储测试不作为本轮验收要求。

1. 应用入口、配置、统一错误与请求 ID，完成 API 存活检查。
2. 内存队列、Worker 生命周期、模拟任务提交和状态查询。
3. 验证正常完成、任务失败隔离、队列容量、应用关闭等关键行为。
4. 逐步接入 MongoDB、MinIO、MinerU、Milvus 和模型，开发相应业务模块。

测试不得默认访问真实外部设施；需要实库或模型的测试单独启用并记录条件。每次实际开发后更新 README 和《后端项目开发日志》，区分目录预留、已实现能力与已经验证的行为。
