# MinerU 文档切分思路

核心流程：**按页顺序读取 → 按小节归集内容 → 每个小节内按长度生成 chunk。**

## 1. 按页顺序读取

以 MinerU 的 `content_list_v2.json` 为主要输入，按外层页面顺序、页内记录原有顺序读取。JSON 数组只是内容容器，其中每条记录可能是标题、段落、列表、表格或图片，不直接等于一个 chunk。

- 提取文字时，同时保留记录的页码和区域坐标。
- 过滤明确标注的页眉、页脚、页码；目录和参考文献默认不进入普通问答检索。
- 保持 MinerU 给出的阅读顺序，不按坐标重新排序，避免双栏内容交错。

**页是读取顺序，不是切分边界。** 同一个小节跨页，仍然可以归集在一起。

## 2. 按小节归集

遇到标题，更新当前标题路径；后续内容归入这个小节，直到遇到下一个标题。

例如 `3 确诊后` 与 `3.1 为什么得癌的是我？`，标题路径为：

```text
3 确诊后 > 3.1 为什么得癌的是我？
```

优先利用明确的章节编号判断父子关系，没有编号时使用 MinerU 的标题层级。不补造缺失的标题。

不同小节不为了凑长度合并。普通正文按顺序归集；表格、图片说明等保留在所属小节中，单独处理，不混进普通正文。

## 3. 小节内生成 chunk

长度使用本地 BGE-M3 的 tokenizer 计算，初始目标约 **500 tokens**，上限 **800 tokens**，包含送入向量模型的标题前缀。

1. 依次加入完整段落，长度合适就继续聚合。
2. 加入下一段会超上限时，先提交当前 chunk，下一段放入新 chunk。
3. 单段本身超长时，先按句子拆；单句仍超长，再进一步切短，不能截断丢文。
4. 小节很短就保留短 chunk，不跨小节填充。
5. 同小节连续正文可保留少量完整句子重叠，最多约 80 tokens；空间不足时减少或取消重叠。

因此：**多条 JSON 记录可以合成一个 chunk，一条超长记录也可以拆成多个 chunk。** 不要求先把整个小节拼成一个大字符串，可按顺序逐段累计处理。

其他内容处理：

| 类型 | 处理方式 |
|---|---|
| 普通列表 | 优先按完整列表项组合，超长项再拆 |
| 表格 | 根据 HTML 保留行列关系；小表整体保留，大表按行分组并重复表头 |
| 图片、图表 | 有图注或提取文字就独立成块；只有图片时保留资产与位置，不生成虚构文字或空 chunk |
| 脚注 | 独立保留，不猜测它与正文的对应关系 |

无法可靠识别的结构记录为待处理内容，不能静默遗漏后标记成功。

## 4. 聚合示例

```text
读取：
第6页：标题3.1 → 段落A → 段落B
第7页：段落C → 标题3.2 → 段落D

归集：
小节3.1：A、B、C
小节3.2：D

假设 A+B 可容纳，再加 C 会超限：
chunk 1：A+B
chunk 2：C
chunk 3：D
```

如果 A+B+C 都能容纳，就生成一个 chunk；不会因为 C 在下一页就强行拆开。

## 5. 保留来源，支持点击跳转

每个 chunk 保存内容类型、正文、标题路径，以及正文涉及的所有来源区域。`contentType` 取值为 `paragraph`（正文）、`list`（列表）、`table`（表格）、`media_text`（图片或图表说明/提取文字）、`footnote`（脚注）：

```json
{
  "documentId": "文档ID",
  "chunkIndex": 0,
  "contentType": "paragraph",
  "content": "段落A……\n\n段落B……",
  "headingPath": ["3 确诊后", "3.1 为什么得癌的是我？"],
  "sourceLocations": [
    {"pageNumber": 6, "bbox": [0.04, 0.35, 0.48, 0.45]},
    {"pageNumber": 6, "bbox": [0.04, 0.46, 0.48, 0.58]}
  ]
}
```

页码从 1 开始，bbox 为左上角原点、0～1 的区域坐标。本样本 content JSON 的 0～1000 坐标除以 1000 转换。

文字聚合时，来源区域一起保留，不将左右栏合成一个大框；段落被拆开时，各子块继承原段区域。缺少可靠坐标时只保留页码，不编造位置。

点击来源后打开原 PDF，默认跳到第一个来源区域，并标记该 chunk 涉及的区域。第一版定位精度为原段落或表格区域，不承诺逐字高亮。
