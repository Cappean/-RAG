# 医疗智能问诊模块接口设计

更新时间：2026-10-19。本文按当前前端工作台和后端模块边界列出接口范围，不定义字段级参数、请求体和响应体，也不代表接口已经实现。

## 1. 设计范围

接口以 `/api` 为统一前缀，按 `patient`、`consultation`、`knowledge`、`rag` 等后端业务模块划分。核心是患者选择、会话历史、消息问诊与 SSE、指南引用打开；搜索、通知、用户中心等当前页面入口暂未接入实际交互，列为后续能力。

本文与 [后端目录设计.md](后端目录设计.md) 的模块边界、[数据存储设计.md](数据存储设计.md) 的存储约定保持一致。后台任务为 API 单进程内的 `asyncio.Queue`，状态在内存，不设计 MongoDB `jobs` 集合接口。当前旧的 [医疗智能问诊前端接口指南.md](医疗智能问诊前端接口指南.md) 含持久化 jobs、文档版本等过期约定，实施接口时以本文件和当前数据存储设计为准；旧指南尚未同步，本次不覆盖其历史内容。

## 2. 模块和优先级

| 模块 | 页面能力 | 优先级 |
|---|---|---|
| `patient` | 当前咨询对象和切换档案 | 核心联调 |
| `consultation` | 创建会话、历史列表、读取消息、发送消息和 SSE | 核心联调 |
| `knowledge` | 已挂载指南来源、引用对应的文档信息和原文访问 | 核心联调 |
| `attachment` / `consultation` | 随问诊发送检查报告、图像 | 接口需要，数据保存边界待定 |
| `search` / `rag` | 顶部疾病、症状、药品搜索 | 页面入口，交互待实现 |
| `user` / `notification` | 个人中心、通知 | 页面入口，鉴权与业务待实现 |
| `system` | 服务在线状态、能力版本或健康信息 | 可选；静态展示优先由前端配置 |
| 语音 | 麦克风输入 | 优先浏览器本地识别，服务端转写待定 |

## 3. 患者模块 `patient`

支撑当前咨询对象展示与切换。会话创建可关联患者；如患者选择为空，是否允许无患者会话需由业务规则确定。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/patients` | 获取可供当前页面选择的患者列表 |
| `GET /api/patients/{patientId}` | 获取患者档案概要，用于显示姓名、年龄、性别、过敏史等 |
| `POST /api/patients` | 新增患者档案；只有界面提供新增入口时启用 |
| `PUT /api/patients/{patientId}` | 修改患者档案；只有界面提供编辑入口时启用 |

患者数据包括页面当前展示的信息，以及存储设计中确定的过敏史、既往史和当前用药。年龄与出生日期的录入规则尚待确定，不由接口层自行推算不可靠数据。

## 4. 问诊模块 `consultation`

会话、消息、历史列表和消息引用属于问诊模块。患者和会话数据按当前存储设计使用 ObjectId，接口返回字符串形式。

| 方法与路径 | 用途 |
|---|---|
| `POST /api/conversations` | 创建会话，可关联患者 |
| `GET /api/conversations` | 分页读取历史会话，供左侧列表及查看更多使用 |
| `GET /api/conversations/{conversationId}` | 获取会话概要及关联患者信息 |
| `GET /api/conversations/{conversationId}/messages` | 分页读取该会话的完整消息、生成状态和引用快照 |
| `POST /api/conversations/{conversationId}/messages` | 发送首轮问题或后续补充；普通 JSON 消息或按附件方案使用 multipart；启用 SSE 时返回生成事件流 |

消息流至少覆盖：助手消息创建、流程状态、增量文本、引用、完成、错误。检索耗时等本轮运行信息可通过状态或完成事件返回，不要求为一次回答另存模型配置或虚构页面数据。

历史会话计数和更多列表应由分页会话列表提供。前端“进行中、已办结、已随访”状态徽标与当前存储设计冲突：存储设计已取消 `conversations.status`，没有结束问诊操作。确定是否恢复会话分类字段前，不能要求后端伪造该状态；第一版可以由更新时间和标题展示历史，暂不展示这类状态。

消息中的 `citations` 是回答来源快照。页面读取消息即可得到指南名称、引用文本、匹配分数及可用定位，不直接调用 Milvus。具体引用结构需统一采用当前 `chunks.sourceLocations`，不能继续假定旧指南中的 `pageIndex` 足以表示 MinerU 多区域定位。

## 5. 知识库模块 `knowledge`

支撑当前已挂载证据库展示、引用查看和未来知识库管理。知识文档和切片元数据保存在 MongoDB；原始文件和解析产物保存在 MinIO；向量查询由服务端完成。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/knowledge/sources` | 获取当前启用的知识库或指南来源概要，替代侧栏静态来源列表 |
| `GET /api/knowledge/documents` | 分页查询文档；按页面需要筛选可检索、处理中或失败文档 |
| `GET /api/knowledge/documents/{documentId}` | 获取文档名称、原始类型和当前处理状态 |
| `GET /api/knowledge/documents/{documentId}/access-url` | 获取短时有效的原文访问地址，供阅读器打开 PDF 或 Markdown |
| `POST /api/knowledge/documents` | 管理界面上传 PDF/Markdown，创建文档并触发入库 |
| `DELETE /api/knowledge/documents/{documentId}` | 管理界面停用文档并安排清理 |

若知识库管理界面展示正在处理的任务，需要增加基于内存状态的任务查询接口（例如 `GET /api/tasks/{taskId}`）；上传或入库提交时返回 taskId。任务查询只在当前 API 进程生命周期内有效，服务重启后记录丢失。文档的持久化 `status` 表示是否可检索，不能与内存任务状态混为一谈。

旧接口指南中的 `/api/knowledge/jobs/{jobId}` 和 `/retry` 是 MongoDB 持久化队列方案，不适用于当前 demo。第一版不自动重试；如果管理界面确实需要人工重试，应复用或新增显式的入库提交操作，并在同一进程的内存任务模型中报告状态，不建立 `jobs` 集合。

## 6. 搜索模块 `search` / `rag`

顶部搜索按钮目前只有视觉入口，没有搜索弹层或结果页。若将它实现为独立医学搜索，再启用以下接口：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/search/suggestions` | 根据输入内容提供疾病、症状或药品联想 |
| `GET /api/search` | 执行医学知识搜索并返回来源定位 |

独立搜索结果的排序和引用格式应复用 RAG/knowledge 服务的来源校验，不允许浏览器直连 Milvus。若产品决定搜索框仅用于引导开始问诊，则不需要独立搜索接口，直接复用创建会话和发送消息链路。

## 7. 附件能力 `attachment` / `consultation`

当前页面选择一个 PDF、图片或办公文档后，会与补充消息一起发送；目前没有独立上传进度界面。可先在消息接口上采用 multipart 上传，成功后经现有 SSE 流程返回结果，不必为一个附件额外引入上传、查询、重试 API。

但当前数据存储设计明确暂不保存附件和 `attachmentIds`，尚未决定文件的保存位置、保留期限、历史消息访问方式及删除策略。因此，消息 multipart 只是一种候选传输方式，不代表附件会持久关联到消息。接入真实文件问诊前必须确定这些存储和隐私边界；若需要独立上传进度或历史文件访问，再设计附件资源及对应接口。

## 8. 用户与通知模块 `user` / `notification`

个人中心和通知图标目前未实现交互，项目当前也暂不做鉴权和用户集合。以下接口属于后续接入登录与通知能力后的候选范围，不是核心问诊联调前置条件：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/me` | 获取当前登录用户概要 |
| `GET /api/notifications` | 分页获取通知 |
| `GET /api/notifications/unread-count` | 获取未读数，用于通知角标 |
| `POST /api/notifications/{notificationId}/read` | 将一条通知标记为已读 |
| `POST /api/notifications/read-all` | 将当前用户通知全部标记为已读 |

这些接口必须等身份认证、用户归属和通知来源确定后实现，不能在无鉴权阶段暴露其他用户的个人信息或通知。

## 9. 系统状态与语音

页面的知识库在线指示可在确有动态健康状态需求时使用：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/system/status` | 返回经过定义的系统组件可用性摘要；具体检查范围另定 |
| `GET /api/health/live` | 仅检查 API 进程存活，不代表数据库、向量库或模型可用 |

模型名称/版本不应硬编码为虚假的运行状态。只有实际需要显示当前部署版本时，才由服务端提供受控的元数据；单轮检索延迟随问诊 SSE 事件返回即可。若不展示在线状态，页面品牌静态文案无需系统接口。

语音按钮可先采用浏览器本地语音识别，并将识别文本交给普通消息接口，不需要后端语音端点。仅当选择服务端语音识别时，再另行设计音频上传与转写能力；当前没有相关接口。

## 10. 通用协议与联调顺序

- JSON 接口统一 `/api` 前缀、UTF-8、UTC ISO 8601 时间、字符串形式 ID、统一分页结构和错误响应；具体格式沿用前端接口指南中可继续使用的通用约定。
- SSE 是流式协议，事件至少包括状态、token、引用、完成和错误；不能将其包装为普通 JSON。
- demo 暂不鉴权，但所有涉及患者、会话、文档、个人资料和通知的资源操作应预留归属校验位置。
- PDF/Markdown 文件由后端签发短时访问地址；前端不得拼接对象存储地址或持有长期凭据。
- 第一阶段依次联调患者列表/概要、会话增删读、消息历史与 SSE、引用访问；附件接口在明确文件保存策略后联调。
- 搜索、通知、个人中心和语音服务端转写属于后续功能，不阻塞问诊主链路。

## 已做出的决定

- 2026-10-19：接口按 `patient`、`consultation`、`knowledge`、`search`、`attachment`、`user/notification`、`system` 及语音能力归类；核心问诊与尚未实现的页面入口分开标注。
- 2026-10-19：文档与当前目录及存储设计一致；内存任务状态不使用 MongoDB `jobs` 集合，旧前端指南中的持久化 jobs 接口不作为新实现依据。
- 2026-10-19：第一阶段优先打通患者选择、会话和消息、SSE、引用原文访问；搜索、通知、个人中心及服务端语音转写不作为核心链路前置条件。
- 2026-10-19：页面会话状态徽标与当前无会话状态的存储设计存在待决冲突；在业务决定前不新增或伪造会话状态。
- 2026-10-19：页面附件发送能力与当前不持久化问诊附件的存储决定存在待决边界；确认文件保留、归属和历史访问策略前，不承诺附件持久关联。
