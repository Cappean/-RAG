# 医疗智能问诊模块接口设计

更新时间：2026-10-20。本文按当前前端工作台和后端模块边界列出接口范围，不定义字段级参数、请求体和响应体，也不代表接口已经实现。

## 1. 设计范围

接口以 `/api` 为统一前缀，按 `patient`、`consultation`、`knowledge`、`rag` 四个后端业务模块，以及 `worker`、健康检查等公共能力划分。核心是患者选择、会话历史、消息问诊与 SSE、真实检索与生成、指南引用打开；附件、独立搜索、通知、用户中心和语音列为后续功能，具体代码归属另行说明。

项目所有查询均不分页。列表查询一次返回当前查询范围内的全部结果，可按业务条件筛选和排序，不设置页码、游标、每页条数或默认截断，不要求前端通过“下一页”或“加载更多”获取剩余数据。

本文与 [后端目录设计.md](后端目录设计.md) 的模块边界、[数据存储设计.md](数据存储设计.md) 的存储约定保持一致。后台任务为 API 单进程内的 `asyncio.Queue`，状态在内存，不设计 MongoDB `jobs` 集合接口。

当前接口范围及通用协议以本文为依据，不依赖已移入 `doc/舍弃` 的前端接口指南、前端验收说明或后端整体设计方案。仍保留的《后端项目框架设计》包含旧目录、MongoDB 持久化任务及独立 Worker 方案；这些内容已由当前目录设计和数据存储设计取代，不作为接口实现依据。

## 2. 模块和优先级

| 后端模块或公共能力 | 目录归属 | 负责内容 | 优先级 |
|---|---|---|---|
| `patient` | `src/app/modules/patient/` | 患者档案、当前咨询对象和切换档案 | 核心业务与联调 |
| `consultation` | `src/app/modules/consultation/` | 会话、消息、生成状态、历史引用快照与 SSE | 核心业务与联调 |
| `knowledge` | `src/app/modules/knowledge/` | 文档入库、切片元数据、指南来源和原文访问 | 核心业务；为真实检索提供知识数据 |
| `rag` | `src/app/modules/rag/` | 查询构造、检索、融合、证据校验与回答生成；独立重排后续接入 | 真实问诊核心，由问诊模块调用 |
| `worker` | `src/app/worker/` | 单进程内存任务执行、异常隔离与状态查询 | 框架基础，先于真实异步入库接入 |
| 健康检查 | `src/app/modules/health.py` | API 存活检查 | 框架基础 |

表中业务重要性与开发顺序分别说明：先实现应用入口、配置、错误处理、日志、健康检查和内存任务，再逐步开发业务模块。业务联调先打通患者、会话及消息，再接入真实文档入库、RAG 和原文访问。模拟回答可用于早期联调，但不代表真实问诊链路已完成。

模块不要求各自都有独立 HTTP 接口：`rag` 可以通过内部 Service 为 `consultation` 提供能力。附件、独立搜索、用户通知、动态组件状态和语音的候选接口统一列在“后续功能及待定归属”，不据此默认新增同名业务目录。

## 3. 患者模块 `patient`

支撑当前咨询对象展示与切换。会话创建可关联患者；如患者选择为空，是否允许无患者会话需由业务规则确定。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/patients` | 一次获取符合筛选条件的全部患者概要，供页面选择 |
| `GET /api/patients/{patientId}` | 获取患者档案概要，用于显示姓名、年龄、性别、过敏史等 |
| `POST /api/patients` | 新增患者档案；只有界面提供新增入口时启用 |
| `PUT /api/patients/{patientId}` | 修改患者档案；只有界面提供编辑入口时启用 |

患者数据包括页面当前展示的信息，以及存储设计中确定的过敏史、既往史和当前用药。年龄与出生日期的录入规则尚待确定，不由接口层自行推算不可靠数据。

## 4. 问诊模块 `consultation`

会话、消息、历史列表和消息引用属于问诊模块。患者和会话数据按当前存储设计使用 ObjectId，接口返回字符串形式。

| 方法与路径 | 用途 |
|---|---|
| `POST /api/conversations` | 创建会话，可关联患者 |
| `GET /api/conversations` | 一次读取符合筛选条件的全部历史会话概要，供左侧列表使用 |
| `GET /api/conversations/{conversationId}` | 获取会话概要及关联患者信息 |
| `GET /api/conversations/{conversationId}/messages` | 一次读取该会话的全部消息、生成状态和引用快照 |
| `POST /api/conversations/{conversationId}/messages` | 发送首轮问题或后续补充；普通 JSON 消息或按附件方案使用 multipart；启用 SSE 时返回生成事件流 |

消息流至少覆盖：助手消息创建、流程状态、增量文本、引用、完成、错误。检索耗时等本轮运行信息可通过状态或完成事件返回，不要求为一次回答另存模型配置或虚构页面数据。

历史会话计数可由返回列表计算，无需分页计数或额外的更多列表接口。会话按最近更新时间排序，消息按时间顺序返回，同时间记录的稳定排序规则在详细设计中明确。界面折叠只影响已获取数据的展示，后端仍返回符合条件的全部记录。

前端“进行中、已办结、已随访”状态徽标与当前存储设计冲突：存储设计已取消 `conversations.status`，没有结束问诊操作。确定是否恢复会话分类字段前，不能要求后端伪造该状态；第一版可以由更新时间和标题展示历史，暂不展示这类状态。

消息中的 `citations` 是回答来源快照。页面读取消息即可得到指南名称、引用文本及可用定位，不直接调用 Milvus。引用结构遵循当前数据存储设计，来源定位采用 `sourceLocations`，支持 PDF 页码与多个区域，以及原生 Markdown 行号；没有可靠定位时只打开原文件。当前引用快照不保存匹配分数，不要求历史消息展示该数据。

## 5. 知识库模块 `knowledge`

支撑当前已挂载证据库展示、引用查看和未来知识库管理。知识文档和切片元数据保存在 MongoDB；原始文件和解析产物保存在 MinIO；向量查询由服务端完成。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/knowledge/sources` | 一次获取全部当前启用的知识库或指南来源概要，替代侧栏静态来源列表 |
| `GET /api/knowledge/documents` | 一次查询符合条件的全部文档概要；可筛选可检索、处理中或失败文档 |
| `GET /api/knowledge/documents/{documentId}` | 获取文档名称、原始类型和当前处理状态 |
| `GET /api/knowledge/documents/{documentId}/access-url` | 获取短时有效的原文访问地址，供阅读器打开 PDF 或 Markdown |
| `POST /api/knowledge/documents` | 管理界面上传 PDF/Markdown，创建文档并触发入库 |
| `DELETE /api/knowledge/documents/{documentId}` | 管理界面停用文档并安排清理 |

上传或入库实际创建任务并成功入队时，返回文档标识和 taskId，界面通过 `worker` 提供的任务查询接口读取状态；重复上传仅返回已有文档及状态时，不虚构新的 taskId。文档持久化 `status` 表示是否可检索，内存任务状态表示一次处理的执行结果；知识库模块负责文档业务，通用队列与状态查询由 `worker` 负责。

“停用并安排清理”的具体范围仍待确认：现有存储设计优先停用并保留原文件，以支持历史引用；不能在尚未敲定清理策略时直接删除文件。

当前 demo 不设计持久化 jobs 查询或自动重试接口。第一版不自动重试；如果管理界面确实需要人工重试，应复用或新增显式的入库提交操作，并在同一进程的内存任务模型中报告状态，不建立 `jobs` 集合。

## 6. 检索与生成模块 `rag`

`rag` 是真实问诊的内部核心模块，承担查询构造、BGE-M3 稠密与稀疏召回、RRF 融合、证据与回答校验及模型生成。首期 BGE-M3 在 CPU 上推理，暂不加载独立 Reranker，按融合排序选择可用证据后交给 DeepSeek；重排作为后续优化能力。它的优先级不取决于是否开发顶部独立搜索入口。

当前不单独设计 `/api/rag` 接口。由 `consultation` 接收消息并调用 RAG Service，再由问诊模块持久化消息和引用快照、输出 SSE。`knowledge` 提供文档及切片的业务访问能力，`infrastructure` 封装 Milvus 和模型底层调用，跨模块通过明确的 Service 方法和数据结构协作。

查询接口返回全部历史消息，不意味着必须将全部历史塞给模型。模型上下文预算、召回候选数和重排保留数属于 RAG 算法配置，不是查询接口的分页参数，也不能用于截断患者、会话、文档或消息列表。

## 7. 内存任务公共能力 `worker`

代码位于 `src/app/worker/`，在应用生命周期内创建有界 `asyncio.Queue`、状态字典和消费协程。它负责通用任务执行和状态管理，文档处理器调用 `knowledge` Service 完成业务流程。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/tasks/{taskId}` | 查询当前进程中一项内存任务的状态、进度和结果摘要 |

任务通过知识库等业务提交入口入队，不向前端开放任意处理器名称或任意函数执行。框架阶段的模拟任务入口仅用于演示验证，具体开发入口与实现一起确定，不混同为正式知识库接口。

任务状态为 `queued`、`running`、`succeeded`、`failed`，查询只在当前 API 进程生命周期及记录保留期内有效；重启或记录被清理后返回任务不存在，不报告成功。任务记录保留限制属于内存生命周期，不是查询分页。

API 单进程运行，不建 MongoDB `jobs` 集合，不提供独立 Worker 进程、自动重试或重启恢复。队列满时明确拒绝提交，不先报告已接收再丢弃任务。文档重试属于业务入库操作，具体入口另行确定。

## 8. 健康检查公共能力

基础存活检查归属 `src/app/modules/health.py`，通过统一路由汇总注册，不单独建立 `system` 业务模块。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/health/live` | 仅检查 API 进程存活，不代表数据库、向量库或模型可用 |

## 9. 后续功能及待定归属

以下内容保留前端功能覆盖范围，候选接口不等于已决定新增同名后端模块。独立目录是否需要拆分，在对应能力确定进入开发后再决定。

| 功能 | 当前归属建议或待定边界 | 优先级 |
|---|---|---|
| 问诊附件 | 优先在 `consultation` 内协调，解析使用外部设施适配；是否独立拆包待定 | 存储与处理边界确认后接入 |
| 独立医学搜索 | 可复用 `rag` 与 `knowledge` Service；HTTP 路由放置位置后续确定，不预设 `search/` 模块 | 搜索交互与业务确认后接入 |
| 个人中心、通知 | 当前无对应业务模块，先确定鉴权、用户归属和通知来源，再决定是否增加模块 | 后续能力 |
| 动态组件状态 | 可扩展公共健康检查能力，具体文件组织待定，不预设 `system/` 模块 | 确有动态状态需求时接入 |
| 语音输入 | 优先评估浏览器识别；若需服务端转写，再确定路由和代码归属 | 后续能力 |

### 9.1 问诊附件

当前页面选择一个 PDF、图片或办公文档后，会与补充消息一起发送；目前没有独立上传进度界面。消息接口采用 multipart 只是候选方案，不据此新增 `attachment/` 业务模块或独立上传、查询、重试 API。

当前数据存储设计明确暂不保存问诊附件和 `attachmentIds`，尚未决定保存位置、保留期限、历史访问和删除策略。接入真实文件问诊前必须确认这些边界；问诊报告不能直接当作公共知识库文档入库。

### 9.2 独立医学搜索

顶部搜索目前只有页面入口；若决定实现独立医学搜索，再启用以下候选接口：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/search/suggestions` | 获取匹配输入条件的疾病、症状或药品联想结果，不分页 |
| `GET /api/search` | 获取符合搜索条件的结果及来源定位，不分页；语义检索候选集的算法规则后续明确 |

独立搜索复用 RAG 的检索与来源校验能力，浏览器不直连 Milvus。若搜索框只是开启问诊的入口，则复用创建会话和发送消息接口，无需独立搜索接口。

### 9.3 个人中心与通知

个人中心和通知图标目前未实现交互，项目当前暂不做鉴权和用户集合。以下为后续候选接口，代码模块归属尚未确定：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/me` | 获取当前登录用户概要 |
| `GET /api/notifications` | 一次获取符合筛选条件的全部通知 |
| `GET /api/notifications/unread-count` | 获取未读数，用于通知角标 |
| `POST /api/notifications/{notificationId}/read` | 将一条通知标记为已读 |
| `POST /api/notifications/read-all` | 将当前用户通知全部标记为已读 |

这些接口必须等身份认证、用户归属和通知来源确定后实现，不能在无鉴权阶段暴露其他用户的个人信息或通知。

### 9.4 动态组件状态

页面的知识库在线指示可在确有动态健康状态需求时使用：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/system/status` | 返回经过定义的系统组件可用性摘要；具体检查范围另定 |

模型名称/版本不应硬编码为虚假的运行状态。只有实际需要显示当前部署版本时，才由服务端提供受控的元数据；单轮检索延迟随问诊 SSE 事件返回即可。若不展示在线状态，页面品牌静态文案无需系统接口。

该候选路径不意味着需要新增 `system/` 模块，实际代码归属以公共健康检查能力的扩展设计为准。

### 9.5 语音输入

语音按钮可先评估浏览器语音识别，将识别文本交给普通消息接口；该方式无需后端语音端点。仅当选择服务端语音识别时，再设计音频上传、转写接口和代码归属；当前没有相关接口。

## 10. 通用协议与联调顺序

- JSON 接口统一 `/api` 前缀和 UTF-8 编码；时间采用 UTC ISO 8601 字符串，业务 ObjectId 对外转为字符串，内存任务 ID 使用 UUID 字符串。
- 所有查询不分页：列表一次返回符合业务筛选条件的全部结果，不设计 `page`、`pageSize`、`offset`、`limit`、分页游标及下一页元数据，也不使用隐含默认条数截断。对象详情和按 ID 查询同样无需分页；列表外层响应格式在详细设计时统一。
- HTTP 状态码表达请求结果；错误响应统一提供稳定的业务错误码、可读提示和请求追踪 ID，必要时提供校验错误详情。具体响应结构留待详细设计，不依赖已舍弃文档，也不将内部异常或敏感数据直接返回前端。
- SSE 是流式协议，事件至少包括状态、token、引用、完成和错误；不能将其包装为普通 JSON。
- demo 暂不鉴权，但所有涉及患者、会话、文档、个人资料和通知的资源操作应预留归属校验位置。
- PDF/Markdown 文件由后端签发短时访问地址；前端不得拼接对象存储地址或持有长期凭据。
- 框架开发先实现应用入口、公共配置、日志、统一错误与请求 ID、健康检查，再实现内存任务；随后开发患者、会话与消息，接入知识入库和真实 RAG，最后验证原文访问和定位。
- 核心业务联调覆盖患者列表/概要、会话创建与读取、全部消息历史与 SSE、真实问诊生成和引用访问；当前接口表未设计会话删除，不将其列入首期联调。附件接口在明确文件保存策略后联调。
- 前端与后端均不设计分页或远程加载更多；前端可对已获取列表做折叠、筛选或渲染优化，模型上下文预算和检索候选数量另按 RAG 配置处理。
- 搜索、通知、个人中心和语音服务端转写属于后续功能，不阻塞问诊主链路。

- 2026-10-19：文档与当前目录及存储设计一致；内存任务状态不使用 MongoDB `jobs` 集合，旧前端指南中的持久化 jobs 接口不作为新实现依据。
- 2026-10-19：第一阶段优先打通患者选择、会话和消息、SSE、引用原文访问；搜索、通知、个人中心及服务端语音转写不作为核心链路前置条件。
- 2026-10-19：页面会话状态徽标与当前无会话状态的存储设计存在待决冲突；在业务决定前不新增或伪造会话状态。
- 2026-10-19：页面附件发送能力与当前不持久化问诊附件的存储决定存在待决边界；确认文件保留、归属和历史访问策略前，不承诺附件持久关联。
- 2026-10-19：前端接口指南、前端验收说明和后端整体设计方案已移入 `doc/舍弃`；当前接口设计不再链接或依赖这些文档，通用协议直接在本文维护，字段级格式仍留待详细设计。
