# 项目细节关键决策

更新时间：2026-10-20。

本文按模块记录开始实现前需要明确的关键细节，供逐项讨论、确认和验收使用，不代表相关能力已经实现。

## 1. 使用方式与依据

- **已确认**：来自现有有效设计或本次对话中明确敲定的约定。
- **待确认**：业务行为或实施方式尚未敲定；“建议”仅供讨论，不自动成为需求。
- **后续再定**：不阻塞首期开发，进入对应功能开发前再补齐。

条目编号保持稳定，讨论时可以直接引用，例如“确认 C-03”。确认后更新正文状态，并在文末“已做出的决定”追加对应记录；后续推翻某项决定时，追加新的替代决定，不改写或删除历史决定。

本文参考 [后端目录设计.md](后端目录设计.md)、[数据存储设计.md](数据存储设计.md)、[模块接口设计.md](模块接口设计.md)、[MinerU工具使用说明.md](MinerU工具使用说明.md) 和 [MinerU文档切分方案.md](MinerU文档切分方案.md)。发现冲突时标明冲突并补充决定，不通过本文件中的建议直接覆盖现有约定。

| G-06 | 待确认 | 输入限制和状态码 | 明确消息长度、标题长度、非法 ID、资源不存在、生成冲突、队列满、依赖不可用等边界。建议分别使用明确的 4xx/5xx 响应；SSE 已开始后的错误通过流事件报告。具体限制值进入对应模块时确定。 |

| G-09 | 已确认 | 所有查询不分页 | 列表一次返回符合查询范围和业务筛选条件的全部结果，不设置页码、每页条数、游标或默认截断，不做远程加载更多；前端可折叠已获取的数据。RAG 候选数量和模型上下文预算另行配置，不用于截断业务列表。 |

| P-02 | 待确认 | 首期患者数据从哪里来 | 建议先提供可重复执行的演示数据初始化脚本，支撑列表和概要接口；新增、编辑接口是否首期实现，取决于是否同时提供相应页面入口。 |
| P-03 | 待确认 | 未选择患者能否开始问诊 | 存储允许会话的 `patientId` 为空，但业务是否允许尚未确认。建议允许一般知识咨询不关联患者；不能因此自动生成患者档案或猜测个人信息。 |
| P-04 | 待确认 | 年龄与出生日期录入 | 已明确不能根据一个年龄伪造出生日期。建议首期支持出生日期可空，已知日期时计算年龄，否则显示未知；如必须只录年龄，再补充相应存储设计。 |
| P-05 | 待确认 | 档案修改对历史会话的影响 | 当前会话仅关联患者 ID，没有患者信息快照。需要明确历史界面和后续回答读取最新档案，还是要求保留当时档案。建议 demo 先读取最新档案，并明确不提供历史档案还原。 |

## 4. 问诊模块 `consultation`

| 编号 | 状态 | 关键细节 | 当前约定或建议 |
|---|---|---|---|
| C-01 | 已确认 | 会话与消息状态分离 | 会话不设“进行中、已办结、已随访”状态，不设结束问诊操作。消息状态为 `generating`、`completed`、`failed`，用户消息入库即完成。 |
| C-02 | 待确认 | 标题与创建时机 | 确认点击新建时即创建空会话，还是首条消息时创建；标题由用户输入、首条问题截取，还是模型生成。建议首期点击新建即创建，使用默认标题，首条问题后按固定规则更新，不额外调用模型。 |
| C-03 | 待确认 | 一轮生成期间再次发送 | 已确认同一会话按顺序一轮一答；冲突响应和前端提示尚未确定。建议后端拒绝同一会话并发生成并返回 409，前端生成期间禁用发送；不同会话能否并发还需结合模型容量限制。 |
| C-04 | 待确认 | SSE 事件协议 | 已确认需要助手消息创建、流程状态、增量文本、引用、完成和错误事件。需固定事件名称、消息 ID、载荷示例、终止规则及是否心跳；建议仅保留一套完成事件名称，并约定正常结束和异常结束的区别。 |
| C-05 | 待确认 | 刷新、断连和主动停止 | 建议首期不做流恢复及独立停止接口；连接断开时尽力取消生成，已保存消息标记失败，页面刷新后读取历史状态。若选择断连后继续生成，则需另行明确独立任务生命周期，不能依赖已关闭的请求协程。 |
| C-06 | 待确认 | 超时、部分回答和重启处理 | 已明确应识别重启后遗留的 `generating` 消息。建议将遗留消息标记失败；运行中超时保留已生成文本并标记失败，不自动重发。需确定超时值、部分内容保存时机和展示提示，不必每个 token 写库。 |
| C-07 | 待确认 | 重复提交与失败后的再次提问 | 确认网络重试是否可能重复保存用户消息。建议首期禁止客户端自动重试发送请求，界面拦截重复点击；失败后重新发送按新一轮处理。若要求透明重试，再设计幂等请求标识和存储规则。 |
| C-08 | 待确认 | 历史排序与展示范围 | 会话按最近更新时间排序已确定，历史会话和单会话消息均一次查询全部符合条件的记录。需补充同时间稳定排序规则、消息时间顺序和完整多轮的界面展示方式；界面可折叠数据，模型上下文长度另行控制。 |
| C-09 | 已确认 | 会话删除范围 | 当前接口设计不包含会话删除，首期不引入删除接口；后续有需求时再明确消息级联处理和保留策略。 |

## 5. 知识库与解析模块 `knowledge`

| 编号 | 状态 | 关键细节 | 当前约定或建议 |
|---|---|---|---|
| K-01 | 已确认 | 文件类型与去重 | 知识库支持 PDF 和原生 Markdown；按原始字节 SHA-256 去重，相同文件返回已有文档及状态，内容不同建立新文档，不维护文档版本，不覆盖旧原文件。失败文档不能当作已成功入库。 |
| K-02 | 待确认 | 首期入库入口 | 确认先用脚本导入，还是同时实现上传接口和管理界面。建议先完成可调用的知识库入库 Service，再提供脚本或接口入口，不让解析逻辑依赖管理页面。 |
| K-03 | 待确认 | 上传校验与 Markdown 图片 | MinerU 工具目前对单 PDF 有 200MB 限制，这不等于业务上传上限。需明确接口大小、页数、格式校验及临时文件规则；原生 Markdown 是否允许外部图片或附带本地图片尚未确定，建议首期先支持不带本地图片资产的文本 Markdown。 |
| K-04 | 已确认 | MinerU 本地输出与对象存储 | 本地工具输出到 `后端/data/mineru/<清理后的文件名_时间戳>/`，不额外加 `parser-output` 层；ZIP 自带路径保留。MinIO 产物使用 `knowledge/{documentId}/parser-output/`，这是不同的存储布局。可读本地目录名不替代文档 ObjectId 或内存 taskId。 |
| K-05 | 已确认 | 切分和来源定位原则 | PDF 以 `content_list_v2.json` 为主要输入，按页、小节、token 长度组织；原生 Markdown 直接切分原文。保留章节路径和真实来源位置，缺失保持为空，不让模型补造页码或坐标。 |
| K-06 | 待确认 | 切分参数与特殊内容 | 开始切分实现前核对现有切分方案，固定 tokenizer、目标长度、最大长度、重叠、长表格及空内容处理规则；通过样本文档验证跨页、多区域和 Markdown 行号，参数由统一配置管理。 |
| K-07 | 待确认 | 多存储写入失败与重新入库 | 文档仅在解析、切分、向量化完成后变为 `ready`。需确定原文件已上传但排队失败、MongoDB 或 Milvus 部分写入失败的处理顺序。建议先标记失败，显式重提时按 documentId 清理未完成产物并防止同文档同时入库，不把跨存储操作假定为一个事务。 |
| K-08 | 待确认 | 停用、清理和历史引用 | 当前接口写“停用并安排清理”，存储设计倾向停用并保留原文件。建议首期只改为 `disabled`，从新检索中排除，保留原文件和历史快照；物理删除、向量清理时机及处理中能否停用另行决定。 |
| K-09 | 待确认 | 文档来源列表的含义 | 需明确 `/knowledge/sources` 是按单份文档展示，还是按知识库分组。现有存储未定义独立知识库分组集合；建议首期展示 `ready` 文档摘要，不为静态名称虚构分类资源。 |

## 6. 检索与生成模块 `rag`

| 编号 | 状态 | 关键细节 | 当前约定或建议 |
|---|---|---|---|
| R-01 | 已确认 | 检索与生成主链路 | BGE-M3 生成稠密、稀疏表示，Milvus 双路检索，RRF 融合，MongoDB 读取正文和定位并过滤非 `ready` 文档，按融合排序选择证据并校验，DeepSeek 生成。首期暂不使用独立 Reranker，真实加载和效果仍需验证。 |
| R-02 | 待确认 | 模型加载与 DeepSeek 调用 | 本地 BGE-M3 使用 CPU、暂不使用独立 Reranker 已确认，见 R-07；本地目录已找到。具体加载适配与 DeepSeek 模型调用仍需验证，密钥只通过服务端配置提供。LangChain/LangGraph 是否首期引入尚需确定，不预先认定已安装或接入。 |
| R-03 | 待确认 | 检索与上下文预算 | 需确定各路召回条数、融合条数、重排保留条数、证据 token 上限、历史轮数和回答 token 上限。建议集中配置，以实际样本调参，不把分数直接解释为医学结论可信概率。 |
| R-04 | 待确认 | 没有证据与依赖失败 | 需区分“检索正常但没有匹配证据”和“Milvus、模型等调用失败”。建议前者明确说明未找到证据并按已确认策略回答或追问，后者报告失败；是否允许无证据时使用通用模型知识，需要业务确认，不自动降级为假成功。 |
| R-05 | 已确认 | 引用真实性 | 引用嵌入助手消息，保存来源名称、原文、文档及切片 ID、章节和定位快照；不存临时 URL，不要求历史消息提供未保存的匹配分数。引用文本与位置来自真实检索证据。 |
| R-06 | 待确认 | 回答内容与界面结构 | 当前消息以正文和引用为主，需明确“分析、建议”等页面区块由 Markdown 标题展示还是结构化返回；建议首期用统一 Markdown 正文和引用列表，避免为前端示例区块虚构未保存字段。同时明确何时应追问、何时提示信息不足及回答的医疗用途边界。 |
| R-07 | 已确认 | CPU 与首期关闭重排 | BGE-M3 使用 CPU 推理，首期不下载、不加载独立 Reranker；在配置中记录 CPU 和重排关闭，待实现配置加载与模型适配后生效。已找到模型文件不代表已完成加载、推理或性能验证。 |

## 7. 内存任务模块 `worker`

| 编号 | 状态 | 关键细节 | 当前约定或建议 |
|---|---|---|---|
| W-01 | 已确认 | 队列与任务状态 | 单个 API 进程内的 `asyncio.Queue` 加状态字典；状态为 `queued/running/succeeded/failed`；UUID taskId，重启后失效。不引入 Redis、Celery、MongoDB jobs、独立 Worker 进程或自动恢复。 |
| W-02 | 待确认 | 容量、并发和记录保留 | 已要求限制队列及已完成记录，但具体容量、消费并发、记录数量或保留时间未定。建议从单消费协程起步，配置化限制，队列满时明确拒绝；不能先返回接收成功再静默丢弃任务。 |
| W-03 | 待确认 | 状态查询与手动重提 | 需确定任务查询响应、进度阶段、轮询间隔及业务入库重新提交入口。重启后查旧 taskId 返回任务不存在，页面仍可通过持久化文档状态判断是否可用；手动重新入库创建新任务，不复活旧内存记录。 |
| W-04 | 已确认 | 启停与异常隔离 | 应用启动时创建协程 Worker，关闭时清理；单个任务失败不能使消费循环退出。单进程启动时处理遗留 `processing` 文档，不自动恢复旧任务。同步解析和推理不能直接阻塞事件循环。 |
| W-05 | 待确认 | 同步解析的关闭行为 | MinerU 当前是同步调用，可交给线程执行；取消协程不会停止已开始的线程或远端解析。需明确关闭等待期限、迟到结果处理和本地临时文件清理，不把取消等待等同于解析已停止。 |

## 8. 原文访问与前端联调

| 编号 | 状态 | 关键细节 | 当前约定或建议 |
|---|---|---|---|
| F-01 | 已确认 | 原文访问方式 | 后端签发短时访问地址，MongoDB 不保存签名 URL，前端不持有对象存储长期凭据。PDF 打开原 PDF，原生 Markdown 打开对应原文。 |
| F-02 | 待确认 | 链接过期与浏览器访问 | 需确定 URL 有效期、过期重新获取方式、浏览器可访问的 MinIO 地址及跨域配置。PDF 阅读还需验证 Range 请求，Markdown 阅读需明确资源相对路径如何解析。 |
| F-03 | 待确认 | 阅读器定位能力 | 数据约定已支持 PDF 页码、多区域 bbox 和 Markdown 行号；具体阅读器、区域高亮与行号到 DOM 的映射仍需实现。建议分步验收打开原文、定位、再高亮，不能仅凭存有 bbox 就宣称前端已支持高亮。 |
| F-04 | 待确认 | 前端旧协议适配 | 当前前端适配层仍有旧会话状态、旧页码和匹配分数映射，历史内容处理也偏向最近一轮。建议随对应模块联调同步改为当前协议，并通过显式配置切换 mock/server 模式；服务端失败不静默退回模拟数据。 |
| F-05 | 待确认 | 开发代理与 CORS | 确认实际前端目录、5173 开发服务、后端端口与 API 地址。建议开发期由 Vite 代理 `/api`，如需直接跨域再配置精确的允许来源，避免启动说明与实际访问方式不同。 |
