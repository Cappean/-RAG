# 医疗智能问诊数据存储设计

更新时间：2026-10-19。本文件替代旧数据库设计。本次只重写文档，不修改代码、不连接数据库、不做联调；索引暂不讨论。

## 1. 已确认的取舍

- PDF 使用 MinerU 解析，以 `content_list_v2.json` 为主要切分输入：按页顺序读取 → 按小节归集 → 小节内按 token 长度切分。生成的 Markdown 用于阅读或导出。
- 去掉文档版本及相关字段；原始文件按 SHA-256 去重，内容不同建立新文档，不覆盖旧文档的原文件。
- 去掉 `blockId`，保留切片顺序和实际能够取得的来源位置。
- 暂不做鉴权、用户集合、问诊报告附件，不保存消息的 `attachmentIds`。
- 保留 `ownerId` 作为归属预留，开发阶段统一为 `null`，不代表已经实现权限控制。
- 会话没有“结束问诊”操作，去掉会话状态；消息仍需区分生成中、成功和失败。
- 第一版同一会话按顺序一轮一答，暂不保存 `replyToMessageId`。
- `citations` 嵌入消息，不是独立集合。
- 不保存解析工具名称、解析工具版本和 `markdownAnchor`。
- Demo 阶段使用内存任务队列，不建立 `jobs` 集合；Milvus 采用 BGE-M3 稠密与稀疏混合检索。
- 已验证当前 MinerU 样本的标题、页码与区域坐标；其他文档仍需校验，无法可靠取得的字段保持为空，不由模型猜测填充。

## 2. 存储分工与约定

| 存储 | 内容 |
|---|---|
| MongoDB | 患者、会话、消息、文档信息、切片正文与定位 |
| Milvus | 切片稠密向量、稀疏向量和关联 ID |
| MinIO | 原始 PDF/MD、生成的 Markdown、图片、MinerU 原始产物 |
| API 进程内存 | 待执行任务、任务状态及执行进度；重启后丢失 |
| 开发日志文档 | 开发过程、决策和验证结果，不写入数据库 |

MongoDB 数据库：`medical_consultation`。五个集合：`patients`、`conversations`、`messages`、`documents`、`chunks`。

业务集合 ID 使用 ObjectId，对外转成字符串；Milvus 使用相应字符串关联。内存任务 ID 使用 UUID 字符串，与业务文档 ID 分开。业务时间保存为 UTC 的 MongoDB Date，对外返回 ISO 8601 字符串。

## 3. MongoDB 集合

### patients：患者档案

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 患者唯一 ID |
| `ownerId` | ObjectId / null | 数据归属预留，开发阶段为空 |
| `name` | String | 患者姓名或称呼 |
| `gender` | String / null | 性别，未知时为空 |
| `birthDate` | Date / null | 出生日期，用于计算年龄；未知时为空 |
| `allergies` | Array[String] | 过敏史，默认空数组 |
| `medicalHistory` | Array[String] | 既往病史，默认空数组 |
| `medications` | Array[String] | 当前用药，默认空数组 |
| `createdAt` | Date | 创建时间 |
| `updatedAt` | Date | 最近更新时间 |

只知道年龄时不伪造出生日期；具体年龄录入方式另定。

### conversations：问诊会话

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 会话唯一 ID |
| `ownerId` | ObjectId / null | 会话归属预留 |
| `patientId` | ObjectId / null | 对应患者，未关联时为空 |
| `title` | String | 历史列表展示标题 |
| `createdAt` | Date | 创建时间 |
| `updatedAt` | Date | 最近消息更新时间，用于历史列表排序 |

一个患者可以有多个会话，一个会话包含多条消息。模型回答结束不表示会话结束，不设置 `active/closed`。

### messages：问诊消息

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 消息唯一 ID |
| `conversationId` | ObjectId | 所属会话 ID |
| `role` | String | `user` 用户或 `assistant` 助手 |
| `content` | String | 正文，生成中可为空或为部分文本 |
| `status` | String | `generating` 生成中、`completed` 完成、`failed` 失败；用户消息入库即完成 |
| `citations` | Array[Object] | 本回答的引用快照；无引用时为空数组 |
| `createdAt` | Date | 创建时间 |
| `updatedAt` | Date | 内容或状态最近更新时间 |

消息独立存储，不把全部消息塞进一个会话文档。状态用于区分完整回答与中断回答；开始生成、完成、失败时更新，不必每个 token 写库。重启后需识别并处理遗留的生成中消息。

`citations` 是消息中的嵌套数组，每项如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunkId` | String | 被引用切片的 ID |
| `documentId` | String | 来源文档 ID，用于查找原文件 |
| `documentName` | String | 回答生成时的来源名称快照 |
| `quote` | String | 核实来自检索内容的引用原文 |
| `headingPath` | Array[String] | 可选章节路径快照，无可靠标题则为空 |
| `sourceLocations` | Array[Object] | 可选来源位置快照，PDF 和原生 MD 的结构见 chunks；无法取得则为空 |

快照保留历史引文和定位，不保存临时文件 URL。来源位置由解析、切分程序传递，不能让大模型编造。原文件被删除后，快照不能替代原文件，因此优先停用文档并保留文件。

### documents：知识库文档

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 文档唯一 ID，一份原始文件对应一条记录 |
| `ownerId` | ObjectId / null | 文档归属预留 |
| `name` | String | 展示名称，默认原文件名，可修改 |
| `fileName` | String | 上传时的原始文件名 |
| `sourceType` | String | 原始类型：`pdf` 或 `md`，决定阅读方式 |
| `contentHash` | String | 原始文件字节的 SHA-256，用于去重 |
| `status` | String | `processing` 处理中、`ready` 可检索、`failed` 失败、`disabled` 停用 |
| `originalObjectKey` | String | MinIO 原始 PDF 或 MD 的对象键，用于阅读；原生 MD 同时作为切分输入 |
| `parserOutputPrefix` | String / null | MinerU 解析产物的存储前缀，从中查找切分用 JSON、生成的 Markdown 和图片；原生 MD 为空 |
| `createdAt` | Date | 创建时间 |
| `updatedAt` | Date | 最近状态或元数据更新时间 |

`sourceType` 始终表示上传原文件的类型：PDF 经 MinerU 生成 Markdown 后仍为 `pdf`，前端打开原始 PDF；原生 Markdown 为 `md`，前端使用 Markdown 阅读器。解析工具固定为 MinerU，部署版本由依赖或部署记录管理，不在每份文档上重复保存。

不单独保存 `markdownObjectKey` 和 `assetsPrefix`：PDF 解析生成的 Markdown、图片均从 `parserOutputPrefix` 下查找。PDF 切分主要读取其中的 `content_list_v2.json`，不依赖生成的 Markdown；原生 MD 直接读取 `originalObjectKey`。

只有 `ready` 文档参与回答检索。上传成功只是文件已接收，解析、切分、向量化完成后才能标记可用。

去重流程：计算文件哈希 → 查询已有记录 → 相同则返回已有记录及状态，不重复保存、解析；不同则创建新文档。已有文档失败时重试处理任务，不视为入库成功。哈希只识别字节完全相同的文件，PDF 元数据变化也可能改变哈希。

### chunks：知识切片

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 切片 ID，字符串形式关联 Milvus `chunkId` |
| `documentId` | ObjectId | 所属文档 ID |
| `chunkIndex` | Integer | 文档内切片顺序，从 0 开始 |
| `contentType` | String | 内容类型：`paragraph` 正文、`list` 列表、`table` 表格、`media_text` 图片或图表说明/提取文字、`footnote` 脚注 |
| `content` | String | 切片正文，供重排和回答使用 |
| `headingPath` | Array[String] | PDF 从 MinerU 标题及章节编号整理的层级；原生 MD 从标题整理，无可靠标题则为空 |
| `sourceLocations` | Array[Object] | 原始 PDF 区域或 Markdown 行号列表；允许一个切片对应多个位置，无可靠映射则为空 |
| `createdAt` | Date | 创建时间 |

`sourceLocations` 每项字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `pageNumber` | Integer / null | PDF 物理页序，从 1 开始，不是印刷页码；Markdown 来源为空 |
| `bbox` | Array[Number] / null | PDF 区域 `[左, 上, 右, 下]`，左上角为原点，归一化为 0～1；只有页码时为空；Markdown 来源为空 |
| `startLine` | Integer / null | 原生 Markdown 原文起始行号，从 1 开始；PDF 来源为空 |
| `endLine` | Integer / null | 原生 Markdown 原文结束行号，从 1 开始，包含该行；PDF 来源为空 |

每个位置对象按来源类型填写对应字段：PDF 填 `pageNumber`、`bbox`；原生 MD 填 `startLine`、`endLine`。不需要的字段省略或设为 `null`，不得混用两种位置。原生 MD 的行号必须来自实际切分输入文件，不能来自重新格式化后的文本。

```json
{
  "chunkIndex": 8,
  "contentType": "paragraph",
  "content": "指南正文……",
  "headingPath": ["临床表现", "腹痛特点"],
  "sourceLocations": [
    {"pageNumber": 12, "bbox": [0.1, 0.8, 0.9, 0.95]},
    {"pageNumber": 13, "bbox": null}
  ]
}
```

原生 MD 的位置示例：

```json
{"startLine": 25, "endLine": 32}
```

小节归集是切分程序的处理过程，不新增小节集合，也不逐条存储 MinerU 解析记录。每个 chunk 保存自己的标题路径；不同内容类型单独成块。只有图片、没有可用文字时不生成 chunk，图片资产仍保留在 MinIO。

页码和区域随结构化内容一起传递：多段聚合时保留各自区域，跨页时保留各页位置，长段拆分后各片继承原段区域。同页多栏不合成一个大框。本样本 content JSON 的坐标已验证为 0～1000，转换后保存为 0～1；其他产物仍需校验坐标含义、页面尺寸和旋转。块级坐标只能高亮对应区域，不等于精确高亮引用句子。

原生 MD 保存原文 `startLine`、`endLine`，前端渲染时将行号范围绑定到段落、列表或表格元素；点击来源后滚动到对应元素并高亮。切分和展示必须使用同一份未修改的 Markdown 原文，否则行号会漂移。暂不保存 `markdownAnchor`。

## 4. Milvus：稠密与稀疏混合检索

同一个 Collection 保存两类向量：

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunkId` | VARCHAR，主键 | MongoDB 切片 ID 的字符串形式 |
| `documentId` | VARCHAR | 所属文档 ID 的字符串形式，用于过滤和清理 |
| `denseVector` | FLOAT_VECTOR，1024 维 | BGE-M3 稠密向量，负责语义召回 |
| `sparseVector` | SPARSE_FLOAT_VECTOR | BGE-M3 学习得到的稀疏表示，补充词项匹配 |

流程：问题生成 dense + sparse → 两路检索 → RRF 融合、去重 → MongoDB 获取正文、定位、文档状态 → 过滤非 ready 文档，必要时补充召回 → Reranker → DeepSeek → 保存消息及引用。

须使用能实际输出 BGE-M3 两种表示的加载方式，普通 Embedding 封装可能只返回稠密向量。该稀疏表示与 Milvus 内置 BM25 不同。SDK、版本支持和效果在后续验证。

正文与定位以 MongoDB 为准，不必全部复制到 Milvus。给模型提供证据前必须校验文档仍可检索，避免使用已停用的文档。

## 5. MinIO 文件组织

```text
knowledge/{documentId}/
├── original.pdf 或 original.md
└── parser-output/       PDF 的 MinerU 产物，保留实际文件名和相对路径
    ├── …_content_list_v2.json
    ├── ….md
    ├── images/
    └── 其他解析产物
```

PDF 的 `originalObjectKey` 指向原文件，`parserOutputPrefix` 指向解析产物目录。生成的 Markdown 和 JSON 按明确的文件匹配规则查找；存在多个候选时应明确选择，不能随便读取第一个文件。图片对象键由解析产物中的相对路径与该前缀组合，不根据文件名猜测，也不另行复制到 assets 目录。

原生 MD 的 `originalObjectKey` 同时用于阅读和切分，不复制一份相同文件；`parserOutputPrefix` 为空，不要求存在 parser-output 目录。

MongoDB 保存对象键或前缀，不保存会过期的签名 URL；点击来源时由后端生成临时访问地址。

## 6. 来源跳转的能力边界

| 可靠取得的数据 | 能实现的功能 |
|---|---|
| `documentId` | 打开原文件 |
| 再有 `pageNumber` | PDF 跳到对应页 |
| 再有验证过的 `bbox` | 高亮相应区域 |
| Markdown 的 `startLine`、`endLine` | 滚动到对应渲染元素并高亮 |

当前已用真实 PDF 样本核对 MinerU 内容结构与段落坐标；后续按《MinerU文档切分方案》实现并验证完整切分、跨页和多区域映射。取得不到的数据保持为空，不猜测填充。

现有前端接口指南和后端代码尚未同步这些变更，后续实施时需另行调整。

## 7. Demo 内存任务约定

使用 `asyncio.Queue` 保存待执行任务，使用内存字典按 `taskId` 保存任务状态、进度和结果摘要。任务参数优先传 `documentId` 等引用，不把整份文件放入队列。任务状态为 `queued`、`running`、`succeeded`、`failed`，这些状态不写入 MongoDB。

Worker 是 FastAPI 进程中的后台协程，在应用启动时创建、关闭时清理。API 单进程运行，暂不使用 Celery、Redis、独立 Worker 进程、租约、自动重试或断点恢复。前端轮询任务接口，后端读取内存记录；成功或失败后停止轮询。服务重启后旧任务 ID 失效，查询应明确返回任务不存在。

`documents.status` 继续持久化：文档状态表示“能不能使用”，任务状态表示“一次处理是否完成”。文档入库成功后更新为 `ready`，处理失败时更新为 `failed`。进程异常退出可能留下 `processing` 文档；实现真实入库时，单进程启动后需将上次遗留的记录标记失败，再允许手动重新提交处理，不自动恢复旧任务。重复处理仍需清理部分产物并保证幂等。

内存任务不保证重启后的交付和恢复。队列应有容量限制，完成记录应有数量或保留时间限制，避免长期运行时持续占用内存。持久化队列及自动恢复留待后续优化。
